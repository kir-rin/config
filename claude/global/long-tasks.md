## 긴 작업 — 세션이 끊겨도 이어서 할 수 있게

한 세션에서 끝나지 않을 수 있는 작업은 남는 자리(scratchpad 밖)에 `features.json`(항목·확인 방법·passes)과
`progress.md`(항목마다 한 줄)를 두고, 시작할 때 둘과 `git log`부터 읽는다. **목록을 만들면 구현 전에 사용자에게
보여 주고 승인받은 항목만 구현한다** — 스스로 만든 목록으로 바로 착수하지 않는다. 항목은 한 번에 하나씩 고치고
확인한 뒤 passes를 바꾸고 로컬 커밋으로 체크포인트를 남긴다. subagent·worker에게 맡길 때는 herdr-orchestration 스킬의
"이어서 하기" 절을 따른다.
이어서 할 때 `passes: true` 항목도 그대로 믿지 않는다 — 이전 세션의 보고는 증거가 아니다. 이번에 고칠 항목과 닿는 것은 그 항목의 확인 방법을 한 번 다시 돌려 본다(pstack session-pickup, 2026-10-31).

## 오래 걸리는 일 — 메인이 아니라 subagent 가 (2026-11-08 사용자 결정)

계기: 이름 바꾸기 뒤 시험 하나가 간헐적으로 실패하자 메인이 그 시험을 5번 따로 돌리고 전체 시험을 2번 묶어 돌리려 해, 사용자가 상태를 계속 지켜봐야 했다. 백그라운드 명령도 끝나면 메인이 깨어나 다시 고치고 돌리므로 같은 일이 반복된다 — 메인이 「오래 걸리는 일을 직접 하는 것」이 문제다.

**규칙**
1. 1분 넘을 시험·빌드·대기는 `worker` subagent 하나에 맡긴다(실패 원인 찾기·재시도 포함).
2. 맡길 때 적는 것: **끝 조건**(명령과 기대 출력 — 「통과」가 아니라 `npm test` exit 0 처럼 확인 가능한 것), 쓸 수 있는 경로, 하지 말 것, 단계마다 진행 파일 한 줄. 시간은 끝 조건이 아니라 **예상치**로만 준다.
3. 재시도는 **원인별 1회** — 맥락·메모리 초과면 범위를 줄여, 연결 끊김이면 같은 시작으로, 도구 오류면 다른 모델로. 그래도 안 되면 돌지 말고 멈춰 「어디서·왜」를 보고한다.
4. 메인은 시작할 때 사용자에게 「무엇을, 약 몇 분」 한 줄. 그 뒤 **예상×1.5 에 한 번만** 깨어나(`ScheduleWakeup`) 커밋·파일 변화로 살았는지 본다 — 고정 주기 확인 없음, 상태 글이 아니라 산출물로 판단, **메시지로 깨우지 않음**(쉬던 agent 가 다시 돈다). 변화가 없으면 사용자에게 먼저 한 줄.
5. 끝 보고는 산출물 하나(diff·파일·명령 출력)를 직접 확인하고 받는다.
6. 사용자에겐 되돌릴 수 없는 일(push·배포·바깥 보내기)·진짜 결정만 묻는다. 재시도·flaky·「계속할까요」는 agent 몫.
7. 사용자는 `/ketchup`(pstack)으로 언제든 「지난 말 이후 바뀐 것 · 나를 기다리는 것」을 당겨 볼 수 있다.
8. 세션을 닫아도 이어져야 하는 일은 herdr worker(`workspace-tools.md`).

**`/ketchup` 이 하는 일**(한국어 요약): 사용자가 마지막으로 쓴 메시지 이후 이 대화에서 무엇이 바뀌었는지를 쉬운 말로 알려 주고, 사용자만 정할 수 있는 일(승인·선택·되돌릴 수 없는 일·권한)을 전부 나열해 그 답글만 보고 결정할 수 있게 한다. 읽기만 한다 — 코드·작업·게시를 건드리지 않는다. 무엇이 일어났는지는 100단어 안쪽, 항목마다 30단어쯤, 결정마다 추천·근거·위험을 붙인다. 화면·영상이 있으면 먼저 붙이고, 상태 목록은 그림으로 그리지 않는다.
