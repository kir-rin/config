## 계획을 subagent 로 과업별로 돌릴 때 — 구현 → 검토

계획(과업 여러 개)을 subagent 로 구현 → 검토 순서로 돌릴 때 적용한다(superpowers:subagent-driven-development 포함).
2026-10-28 한 과제의 계획(19과업)에서 과업 하나에 agent 를 4번(구현·검토·수정·재검토) 차례로 띄워 느렸고,
13개 중 10개가 같은 종류의 지적으로 다시 돌았던 것에서 나왔다(사용자 결정).

1. **반복 지적 체크리스트를 누적해 구현 agent 에게 처음부터 준다.**
   - 검토에서 Important 이상이 같은 종류로 2번 나오면 한 줄로 올린다(근거 과업 번호 포함).
   - 15줄을 넘기지 않는다. 더 이상 안 나오는 항목은 뺀다 — 길면 안 읽는다.
2. **어떤 과업이 검토받는 동안 다른 과업 구현을 미리 띄운다.** 단, 둘 다일 때만:
   - 미리 띄울 과업이 「아직 검토 중인 과업」이 만든 인터페이스를 쓰지 않는다
     (검토를 통과해 완료된 과업의 인터페이스는 써도 된다 — 검토 중인 것은 이름·형태가 바뀔 수 있다)
   - 고치는 파일이 겹치지 않는다 → 겹치면 git worktree 로 나누고, 둘 다 검토 통과 뒤 합친다(합친 뒤 전체 테스트)
3. **검토 자리는 줄이고, 모델은 위험으로 고른다.** (2026-10-28 갱신)
   - 과업별 검토는 한 번. 기본은 중간·가벼운 모델, 무거운 검토는 계획 끝 전체 검토에 둔다.
   - 예외: 돈 계산 · 인가 · 개인정보 · 잠금/확정 · 외부 발송이 걸린 과업은 과업별 검토도 가장 좋은 모델 한 번
     (실제로 이 검토가 금액 이중 계산·누락·이중 발송을 잡았다).
   - 작은 수정(한두 파일, 지적 그대로 고침)은 재검토를 생략하고 다음 검토·전체 검토에 맡긴다.
4. **구현 agent 에게는 앞 과업의 이름·타입과 검토에서 넘어온 판정(carry)을 dispatch 에 직접 적는다** — 계획 전체를 읽히지 않는다.
   brief 와 계획의 「Interfaces」 정본이 다르면 정본이 이긴다고 dispatch 에 적는다. 파일 경로·diff 파일·이전 판정을 직접 건네 탐색 턴을 줄인다.
   dispatch 전에 `subagent-templates/task-brief.py <계획> <과업번호> --out <brief>` 로 brief 를 뽑아 그 경로만 준다(계획 전체·결정 파일 통째로 읽히지 않는다). 계획은 폴더 형식(plan.md·constraints.md·interfaces.md·tasks/NN.md)으로 쓰고, brief 는 추측 없이 이어 붙인다.
   결정 파일(decisions.md)의 각 결정에는 `[tags: a, b]` 를 달아 둔다 — brief 가 과업 태그와 겹치는 결정만 고른다(`always` 는 늘 포함).
   구현·수정 dispatch 에는 `고칠 파일:`(path:줄)을 적는다. 계획 과업은 `## 고칠 파일` 절이 필수다(task-brief 가 막는다). 즉석 지시는 dispatch-guard hook 이 막는다. 조사·검토는 첫 줄 `조사:`/`검토:`.
5. **작은 일은 묶어서 한 agent 에게.** 같은 종류 수정 여러 개를 과업마다 따로 돌리지 않는다.
   **반대로 큰 일·서로 독립인 일은 한 agent 에 몰아넣지 않는다** — 따로 떼어 병렬로(필요하면 worktree) 돌린다.
   (2026-10-28: 합치기 + 본 과업 + 독립 기능 2개를 opus agent 하나에 넣었더니 느리고 검토도 무거워졌다.)
6. **구현 모델도 나눈다.** 계획에 코드·값이 거의 다 적힌 기계적인 일은 싼 모델, 판단이 필요한 일만 큰 모델.
7. **서로 기대지 않는 과업은 git worktree 로 나눠 동시에** 돌리고, 둘 다 통과한 뒤 합친다(합친 뒤 전체 테스트).
8. **테스트 범위를 좁힌다.** 과업 중에는 관련 테스트만, 전체 테스트·골든은 커밋 직전에 한 번.
9. **사람 결정은 시작 전에 몰아서 받는다.** 계획의 「사용자 결정 필요」를 실행 전에 모두 묻고 적어 둔다(예: 결정 기록 파일) — 중간에 멈추지 않게.
10. **RED 형식은 minor.** 테스트를 먼저 쓰고 실패 출력을 남기되, 새 모듈이라 「기능 없음」으로 실패해도 검토는 minor 로만 적고
    수정 라운드를 돌리지 않는다. 테스트가 동작을 잡는지는 검토자가 변이(코드를 일부러 깸)로 확인하고, 못 잡으면 important.
    (2026-10-28: 반복 지적 1위(9회)가 이것이라 수정 라운드를 계속 늘렸다.)
11. **superpowers 없이도 돈다.** 틀은 `~/config/claude/subagent-templates/`(구현 규칙·검토 기준·재검토 기준)에 복사해 두었다.
    한 과업 = 구현 → 검토(위 3번 모델) → 지적이 있으면 수정 → (작은 수정이 아니면) 재검토, 최대 3바퀴, 그래도 남으면 멈추고 보고.
    여러 과업은 Workflow 스크립트(사용자가 opt-in 했을 때) 또는 subagent 를 하나씩. 작업 폴더(장부·반복 지적·보고·검토 파일)는
    계획 문서 옆 `sdd/<계획 이름>/` — 코드 레포·공유 레포 안(예: `.superpowers/`)에 두지 않는다.
    subagent 는 `worker` 타입(MCP·스킬 없음, `~/config/claude/agents/worker.md`)으로 띄운다 — Workflow 는 `agent(prompt, { agentType: 'worker' })`.
    (2026-10-28 측정: 일반 subagent 첫 턴 48,484 → worker 14,003 토큰. 이 세션 subagent 259개 중 MCP 도구 호출 0번, 스킬 4번.)
    비용은 자동으로 쌓인다: subagent·워크플로우 agent 가 하나 끝날 때마다 전역 SubagentStop hook(`hooks/agent-cost-hook.py`)이
    이력(`~/.claude/agent-cost/history-YYYY-MM.jsonl`)에 그 agent 한 줄을 더한다(run = 워크플로우 폴더 `wf_…` 또는 agent id).
    메인은 워크플로우·subagent 결과 알림을 받으면 `subagent-templates/agent-cost.py --chart --run <id>` 를 한 번 돌려 대화창에 보여 준다.
    대시보드(아티팩트)와 `--md` 표는 요청할 때만.
12. **눈으로 볼 수 있는 한 줄을 먼저, 그리고 자주 멈춰 본다.** (2026-10-28 — 엔진을 몰아 만들고 화면을 맨 끝에 붙여
    「돌지만 원하던 게 아님」이 늦게 보였다)
    - 계획의 첫 과업은 walking skeleton: 화면→엔진→DB 를 관통해 대표 흐름 한 건이 끝까지 도는 최소 동작.
    - 과업은 층별이 아니라 수직으로 나눈다 — 과업마다 화면에서 보이는 결과가 있게(엔진만 몰아 하고 화면을 끝에 두지 않는다).
    - 계획 승인 때 사용자에게 인수 예시 3~5줄(「이렇게 누르면 이게 보인다」)을 받아 계획에 적는다. 검토 agent 는
      그 줄을 데모에서 직접 밟는다(e2e-capture). 테스트 통과만으로 approved 하지 않는다.
    - walking skeleton 은 관통하되 화면 부품은 하나만(예: 대화 안 표). 첫 과업의 인수 예시는 한 줄로 줄이고, 나머지 부품은 다음 과업에서 붙인다. (2026-10-28 — 첫 과업이 인수 예시 두 줄을 맞추느라 26파일·6층이 됐다)
    - 체크포인트는 인수 시나리오를 Playwright 시험(가짜 AI 대본, 화면 결과만 단언)으로 돌리고, AI 는 캡처를 보고 판단만 한다(sonnet). 고친 문제는 회귀 시나리오로 남긴다. (2026-10-28 — 손 조작 체크포인트가 opus 154번·11분)
    - 새 UX 처럼 방향이 불확실하면 계획 전에 버릴 시제품(스파이크·목업)을 먼저 눌러 보게 한다.
    - worktree 줄을 합칠 때마다, 또는 과업 4~5개마다 데모 체크포인트에서 멈추고 사용자 확인을 받은 뒤 이어 간다.
13. **계획에 시그니처·값을 박아 구현을 「받아 적기」로 만든다.** (2026-10-28 — 화면 과업 구현 16분 중 도구 실행은 2.7분, 나머지는
    모델이 설계를 다시 하며 쓴 출력 127k 였다)
    - 과업마다 만들 함수·도구·카드의 이름·입력·반환 타입, 테스트 이름과 기대값, 등록할 자리를 계획에 적는다. 산문 설명만 두지 않는다.
    - 그렇게 적힌 과업은 싼 모델·낮은 effort 로 돌린다(6번). 과업은 출력 30~40k 안쪽으로 잘게(카드 하나 = 과업 하나).
    - 과업 크기 상한: 화면 부품 하나, 층 5 안쪽, 고칠 파일 시험 포함 10 안쪽. 고칠 파일 목록에 시험·새 파일도 적는다(목록이 실제보다 작게 잡혀 과업 01 이 6 → 26파일이 됐다). task-brief 가 넘으면 경고한다. 실제 크기는 실행 뒤 비용 그림의 바뀐 파일 수로 확인한다.
    - 반복되는 추가 작업(도구·카드·마이그레이션 등)은 생성기 스크립트(`new:*`)와 등록 검사(`check:registry`)가 있으면 계획에 그 명령을 적는다.

전역 지침 목차(`~/.claude/CLAUDE.md`, 사본 `~/config/claude/global/CLAUDE.md`)에서 상황별로 가리킨다 — 자동으로 불러오지 않는다.
